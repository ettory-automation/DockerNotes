O volume bind (também conhecido como bind mount), é a ação de realizar a montagem de um diretório do host, dentro de um container.

Para compreender sobre o assunto abordado e realizar as práticas, iremos seguir os passos a seguir.

* No host, criaremos um diretório dentro de _/tmp_ para exemplificar a técnica:

```shell
cd /tmp
mkdir ./target
```

* Realizaremos agora, a criação de um container com Alpine Linux e entrar em uma sessão do mesmo com um _pseudo-tty_, com o comando abaixo:

```shell
docker run -it -w /app --mount type=bind,source=$(pwd)/target,target=/app alpine sh
```

A flag _-w_ define o diretório de trabalho do container, equivalente a executar _cd /app_ logo ao iniciar.

A flag _--mount_ irá servir para montar um diretório, por meio de parâmetros declarados no comando, assim como visto logo acima.

* Para realizar o teste de montagem, basta que executemos o comando abaixo no container:

```shell
touch file-from-container.txt
```

Neste momento, devemos verificar no _/tmp/target_ do host, se há um arquivo de mesmo nome. Podemos realizar isto, executando o comando abaixo no host:

```shell
ls /tmp/target
```

O bind é bidirecional por natureza. O que significa que a criação de arquivos em _/tmp/target_ no host, também irá afetar o conteúdo presente em _/app_ no container. Podemos realizar a criação de um arquivo dentro de _/tmp/target_ no host para teste, com o comando abaixo:

```shell
touch /tmp/target/file-from-host.txt
```

Logo após realizar a criação do arquivo, basta executar o comando abaixo no container para verificar a existência do mesmo:

```shell
ls /app
```

* Também, de forma menos verbosa, é possível realizar o mount bind deste exemplo, com o comando abaixo:

```shell
docker run -it -w <container_work_directory> -v <directory_host>:<directory_container> <image_name> <command>
```

Neste exemplo:

```shell
docker run -it -w /app -v /tmp/target:/app alpine sh
```

```ad-note
O mesmo realizado aqui, é aplicável à arquivos, bastando apontar o arquivo exato desejado, no path descrito pela flag _-v_, no lado do host e container.
```

## Estudo de caso: aws-cli container

Para visualizarmos o uso efetivo deste tipo de volume na prática, iremos utilizar o exemplo abaixo, onde será configurado o uso de aws-cli no host, sem necessidade de utilização direta da ferramenta no OS:

* Executar _docker pull_ de Docker image para uso de aws-cli (host-side):

```shell
docker pull amazon/aws-cli
```

* Iniciar container com Docker image:

```shell
docker run -it amazon/aws-cli sh
```

Este comando irá informar que foi realizado com sucesso. Porém, o mesmo não foi possível de ser realizado completamente, devido ao _entrypoint_ da imagem, que inicia qualquer comando com o prefixo _aws_. Isto pode ser solucionado, simplesmente limpando o _entrypoint_ da imagem com a flag _\--entrypoint_, como demonstrado com comando abaixo:

```shell
docker run --entrypoint "" -it amazon/aws-cli sh
```

* Podemos listar os buckets presentes na conta AWS, com o seguinte comando dentro do _sh_ do container:

```shell
aws s3 ls
```

Porém este comando não será executado, pois as credenciais da conta AWS não estão presentes no container. Para configurarmos as credenciais da conta AWS no container, basta seguirmos os seguintes passos abaixo, dentro do _sh_ do container:

1. No host, identificar o diretório $HOME/.aws no host (se aws-cli estiver instalado no host):

```shell
find $HOME/ -name ".aws" -type d 2>/dev/null
```

2. Logar no container contendo aws-cli, e montar o diretório localizado no host ($HOME/.aws), para dentro do container:

```shell
docker run --entrypoint "" -it -v $HOME/.aws:/root/.aws amazon/aws-cli sh
```

3. Realizar verificação da presença do diretório no /root do container, e realizar verificação de execução do comando _aws s3 ls_:

```shell
ls -la /root/
aws s3 ls
```

Neste momento, o comando irá ser executado normalmente, devido à existência do arquivo de credenciais da conta AWS, presentes no diretório localizado em _$HOME/.aws_ no host, que está mapeado no container.
