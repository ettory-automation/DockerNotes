## A arquitetura da Docker Engine


![[Docker-Engine.png]]

Como demonstrado no diagrama, a _Docker Engine_ é composta primariamente de dois componentes principais: ***containerd*** e ***runc***. Porém, esta _Engine_ facilita o manuseio destes componentes, abstraindo assim, a necessidade de utilizar destes componentes de forma direta.

O _Docker Client_ não se trata de uma _runtime_ do Docker. Se formos verificar camadas inferiores, perceberemos que existem outras tecnologias sendo consumidas para que o serviço do Docker seja executado. Um exemplo claro disto, está no fato de que o componente responsável por gerenciar o _life cycle_ (_start, stop, pause, delete, etc._) dos _containers_, na realidade seria o _containerd_.

Importante salientar que o motivo pelo qual o Docker não é mais suportado como uma _runtime_ pelo K8s. Há uma clara duplicidade de camadas, envolvendo o uso de _K8s_ juntamente com Docker, sendo que ambos realizam o papel de orquestração (interface simplificada para manipulação de recursos de componentes complexos - Dockerfile) do _containerd_. Sendo assim, a utilização do K8s suprime automaticamente o Docker, para evitar que a arquitetura possua dois orquestradores ao mesmo tempo em execução. Com isso, o resultado final seria a combinação de _containerd_ (_runtime_) + K8s (_orquestrador_), para esta exemplificação.

Já a _runtime_ denominada de _runc_, é a responsável por realmente executar o running dos _containers_. Além disso, o _runc_ é o responsável também por implementar o padrão _OCI_ (_Open Container Initiative_) no Docker, caracterizando o Docker como uma ferramenta _OCI complient_ (Docker < _containerd_ < _runc (OCI complient)_).
