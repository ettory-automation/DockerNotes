# Boas práticas para Dockerfiles

## Use multi-stage builds

**Multi-stage builds** permitem reduzir o tamanho da imagem final, criando uma separação clara entre a construção da imagem e o output final. Separe as instruções do Dockerfile em diferentes stages para garantir que a imagem final contenha apenas os arquivos necessários para executar a aplicação.

Usar múltiplos stages também permite construir de forma mais eficiente, executando etapas de build em paralelo.

Para mais informações: [Multi-stage builds](https://docs.docker.com/build/building/multi-stage/)

---

## Crie stages reutilizáveis

Se você possui múltiplas imagens com muito em comum, considere criar um stage reutilizável com os componentes compartilhados, e basear seus stages únicos nesse stage. O Docker só precisa construir a camada comum uma vez, economizando memória e acelerando o carregamento das imagens derivadas.

Além disso, é mais fácil manter um **common base stage** ("Don't repeat yourself") do que ter múltiplos stages diferentes fazendo tarefas similares.

---

## Escolha a base image correta

O primeiro passo para uma imagem segura é escolher a **base image** certa. Certifique-se de que ela é de uma fonte confiável e mantenha-a pequena.

Tipos recomendados:

- [**Docker Official Images**](https://hub.docker.com/search?image_filter=official): coleção curada, com documentação clara e atualizações regulares.
    
- [**Verified Publisher images**](https://hub.docker.com/search?image_filter=store): imagens de alta qualidade publicadas por organizações parceiras do Docker.
    
- [**Docker-Sponsored Open Source**](https://hub.docker.com/search?image_filter=open_source): mantidas por [projetos open source](https://docs.docker.com/docker-hub/image-library/trusted-content/#docker-sponsored-open-source-software-images) patrocinados pelo Docker.
    

Escolha imagens que exibam os badges desses programas.

---

### Docker Hub Official e Verified Publisher images

Ao construir sua imagem, escolha uma **minimal base image** que atenda aos seus requisitos. Imagens menores oferecem:

- Portabilidade
    
- Downloads rápidos
    
- Menor número de vulnerabilidades
    
- Menor tamanho de imagem
    

Também considere usar duas imagens base: uma para **build e unit testing**, e outra (mais leve) para produção. Ferramentas de compilação e debug não são necessárias na imagem final, reduzindo a superfície de ataque.

## Reconstrua suas imagens frequentemente

Docker images são **imutáveis**. Construir uma imagem cria um snapshot dela naquele momento, incluindo **base images**, bibliotecas e software. Para manter imagens atualizadas e seguras, reconstrua frequentemente com dependências atualizadas.

Para garantir que você está usando as versões mais recentes das dependências:

```bash
docker build --no-cache -t my-image:my-tag .
```

Exemplo de Dockerfile usando _ubuntu:24.04_:

```Dockerfile
# syntax=docker/dockerfile:1
FROM ubuntu:24.04 RUN apt-get -y update \
	&& apt-get install -y --no-install-recommends python3
```

> Dica: considere[ **pinning**](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions) da versão da base image.

## Exclua arquivos irrelevantes com .dockerignore

Use um arquivo _.dockerignore_ para excluir arquivos irrelevantes para o build, sem precisar reestruturar o repositório. Funciona de forma similar ao _.gitignore_.

Exemplo:

_*.md_

Para mais informações: [Dockerignore file](https://docs.docker.com/build/concepts/context/#dockerignore-files).

## Crie containers efêmeros

As imagens devem gerar containers **efêmeros**, ou seja, que podem ser destruídos e recriados rapidamente, com o mínimo de configuração e setup.

Consulte: [Processes under The Twelve-factor App methodology](https://12factor.net/processes)

---

## Não instale pacotes desnecessários

Evite instalar pacotes extras. Por exemplo: não inclua um editor de texto em uma imagem de banco de dados.

Vantagens:

- Redução de complexidade
    
- Menos dependências
    
- Menor tamanho de imagem
    
- Build mais rápido
    

---

## Desacople aplicações

Cada container deve ter **apenas uma responsabilidade**. Separar aplicações em múltiplos containers facilita escalabilidade e reuso.

> Exemplo: uma stack web pode ter três containers separados: web app, banco de dados e cache em memória.

Limitar um container a um processo é uma boa prática, mas não obrigatório:

- Alguns programas podem criar processos adicionais, como [**Celery**](https://docs.celeryq.dev/) ou [**Apache**](https://httpd.apache.org/)
    
- Use [**Docker container networks**](https://docs.docker.com/engine/network/) para comunicação entre containers
    

---

## Organize argumentos de múltiplas linhas

Para listas longas de pacotes, organize os argumentos em múltiplas linhas, alfabeticamente. Facilita manutenção e revisão de PRs.

```Dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
	bzr \
	cvs \
	git \
	mercurial \   
	subversion \   
	&& rm -rf /var/lib/apt/lists/*
```

## Aproveite o build cache

O Docker verifica se cada instrução pode ser reutilizada a partir do [**build cache**](https://docs.docker.com/build/cache/), acelerando builds.

---

## Defina versões fixas da base image

Tags são mutáveis. Para consistência, você pode **pinar uma imagem a um digest específico**:

```Dockerfile
# syntax=docker/dockerfile:1
FROM alpine:3.21@sha256:a8560b36e8b8210634f77d9f7f9efd7ffa463e380b75e2e74aff4511df3ef88c
```

## Instruções Dockerfile

### FROM

Use imagens oficiais atuais como base, de preferência [**Alpine**](https://hub.docker.com/_/alpine/) (pequena e controlada).

---

### LABEL

Adicione labels para organizar imagens e registrar informações:

```Dockerfile
LABEL com.example.version="0.0.1-beta" LABEL vendor1="ACME Incorporated"
```

Multi-line labels:

```Dockerfile
LABEL vendor=ACME\ Incorporated \       com.example.is-beta= \       com.example.is-production="" \       com.example.version="0.0.1-beta" \       com.example.release-date="2015-02-12"
```

---

### RUN

Use **multi-line statements** para facilitar leitura:

``
```Dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \
    package-bar \
	package-baz \
	package-foo
```

Use cache busting e version pinning:

```Dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends \     package-bar \     package-baz \     package-foo=1.3.* \     && rm -rf /var/lib/apt/lists/*
```

---

### CMD

Use a forma exec:


```Dockerfile
CMD ["python"]
```

---

### EXPOSE

Indica portas em que o container escuta:

```Dockerfile
EXPOSE 80
```

---

### ENV

Para variáveis de ambiente:

```Dockerfile
ENV PG_MAJOR=9.3 ENV PG_VERSION=9.3.4 ENV PATH=/usr/local/postgres-$PG_MAJOR/bin:$PATH
```

Evite criar variáveis temporárias em múltiplas camadas:

```Dockerfile
RUN export ADMIN_USER="mark" \     
	&& echo $ADMIN_USER > ./mark \
	&& unset ADMIN_USER
```

---

### ADD ou COPY

- **COPY**: copiar arquivos do contexto do build ou de stages anteriores
    
- **ADD**: suporta download remoto e extração de arquivos _.tar_
    

Exemplo multi-stage com ADD:

```Dockerfile
FROM scratch AS src ARG DOTNET_VERSION=8.0.0-preview.6.23329.7 ADD --checksum=sha256:270d731bd08040c6a3228115de1f74b91cf441c584139ff8f8f6503447cebdbb \     https://dotnetcli.azureedge.net/dotnet/Runtime/$DOTNET_VERSION/dotnet-runtime-$DOTNET_VERSION-linux-arm64.tar.gz /dotnet.tar.gz
```

---

### ENTRYPOINT

Define o comando principal do container:


```Dockerfile
ENTRYPOINT ["s3cmd"] CMD ["--help"]
```

Também pode usar scripts helpers:

```Dockerfile
COPY ./docker-entrypoint.sh / ENTRYPOINT ["/docker-entrypoint.sh"] CMD ["postgres"]
```

---

### VOLUME

Exponha áreas de armazenamento:

```Dockerfile
VOLUME /var/lib/postgresql/data
```

---

### USER

Use um usuário não-root quando possível:

```Dockerfile
RUN groupadd -r postgres && useradd --no-log-init -r -g postgres postgres
```

---

### WORKDIR

Sempre use caminhos absolutos:

```Dockerfile
WORKDIR /usr/src/app
```

---

### ONBUILD

Executa comandos ao construir imagens filhas:

```Dockerfile
ONBUILD COPY . /app ONBUILD RUN make /app
```
