O docker trabalha com um sistema de arquivos em camadas, onde cada camada terá um ID e um tamanho. Neste cenário, devemos compreender que qualquer alteração realizada no momento do build da imagem, irá gerar uma nova camada. Imagine o exemplo descrito a seguir:

> Uma imagem base, de ID _d3a1f33c8a5a_ e de tamanho aproximado de 188.1 MiB será modificada. Dentro de seu arquivo _Dockerfile_, foi executado um comando para instalar um pacote, _sudo apt install_.

Diante deste cenário, devemos compreender que o pacote não será instalado na camada da imagem base, e sim em uma nova camada que será criada logo acima desta, para comportar o pacote instalado. Ou seja, conforme o exemplo dado, segue as movimentações abaixo:

| ID           | Tamanho   | Status            |
| ------------ | --------- | ----------------- |
| c22013c84729 | 194.5 KiB | Pacote instalado  |
| -            | -         | Pacote instalando |
| d3a1f33c8a5a | 188.1 MiB | Imagem base       |

Após todas as movimentações na imagem, obteremos a imagem final. Neste momento, esta imagem acaba de se tornar _read-only_! Isto significa que a partir deste momento, não existe mais a possibilidade de modificar a imagem, restando apenas possibilidades como deletar a imagem, ou criar uma nova imagem baseada nesta, por exemplo.

Quando o _container_ é iniciado, este irá capturar a imagem final e gerar uma camada acima. O que nos dá a compreensão de que o _container_ é apenas uma camada de _read-write_. As movimentações a partir deste momento, com o container em execução, serão realizadas diretamente na camada do container, e não nas camadas da imagem em si, uma vez que este componente (a imagem) leva consigo o princípio da _imutabilidade_.
